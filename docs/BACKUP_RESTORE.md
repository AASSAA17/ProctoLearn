# Резервное копирование и восстановление

`scripts/backup-cli.cjs` сохраняет PostgreSQL в custom-format dump и **все текущие объекты** одного S3 bucket. Manifest содержит SHA256 каждого файла, список таблиц/число строк и ссылки на записи. В dump входят миграции, решения прокторов, апелляции, аудит, уведомления и отметки удаления. `.env`, ключи доступа и исходники инструмент не копирует. Дамп всё равно содержит персональные данные, хеши паролей и служебные токены: храните весь каталог как приватные данные.

Обёртки `scripts/backup.ps1`, `backup.sh`, `restore.ps1`, `restore.sh` передают аргументы этому CLI. Прежние автоматическое копирование `.env`, очистка старых бэкапов и `DROP SCHEMA` удалены. Без аргументов они завершаются ошибкой; последний бэкап автоматически не выбирается.

## Требования и остановка изменений

Нужны Node.js 24 LTS, установленные зависимости backend (`npm ci`) и `pg_dump`, `pg_restore`, `psql` из PostgreSQL той же основной версии, что и сервер. Если они не в PATH, передайте `--pg-bin "C:/Program Files/PostgreSQL/18/bin"` либо соответствующий каталог Linux. Используйте прямое подключение PostgreSQL, без transaction pooler. Требуется доступ ко всем таблицам приложения и текущим объектам bucket.

Перед backup **остановите все API, фоновые обработчики, загрузки, retention и staged-object cleanup**; PostgreSQL и S3 должны работать. Не допускайте новых подключений приложения до завершения команды. CLI отклоняет другие клиентские соединения БД и сравнивает инвентарь до/после, однако эти проверки не доказывают отсутствие всех возможных изменений. `--confirm-quiescent` — явное подтверждение оператором этого окна обслуживания.

Для локального Docker-окружения остановить API и web можно так:

```powershell
docker compose --project-name proctolearn-local --env-file .env.local -f docker-compose.local.yml stop web api
```

У native launcher остановка через Ctrl+C завершает также PostgreSQL и S3. Для нового выделенного release профиля существует безопасное окно обслуживания:

```powershell
node scripts/demo-release.cjs stop
node scripts/demo-release.cjs maintenance
```

Оставьте maintenance в первом терминале. Во втором выполните:

```powershell
node scripts/demo-release.cjs backup rehearsal-01
node scripts/demo-release.cjs restore rehearsal-01
node scripts/demo-release.cjs stop
```

Обёртка работает только с отмеченным профилем `.local/release-demo`, его БД `proctolearn_release` и bucket `proctolearn-release`; приватные ключи читает из конфигурации этого профиля. Backup требует maintenance без API/web. Restore сначала проверяет архив, создаёт новую пустую пару БД/bucket со случайным суффиксом, затем вызывает описанный ниже CLI. Исходные данные не заменяются. Цели и результат записываются в приватный `restore-<suffix>.json`. Для прежнего `.local` окружения по-прежнему нужна ручная остановка writers/запуск зависимостей с исходными настройками. Инструменты не останавливают чужие процессы.

Release wrapper сохраняет приватную конфигурацию, accounts/access file, ownership marker и существующие certificate/scenario evidence в отдельный соседний `<backup>-operator` с хешами. DB/S3 archive остаётся самостоятельным строго проверяемым форматом. Оба каталога приватны; конфигурация не импортируется автоматически и не заменяет действующие настройки. Для проверки восстановления остановите maintenance, запустите `node scripts/demo-release.cjs start-restored restore-<suffix>.json`, затем `node scripts/demo-release-restore-smoke.cjs`. После проверки `stop` и обычный `start` вернут исходную пару.

Backup удерживает PostgreSQL advisory lock `71083208`, который используют операции удаления записей. Это дополнительная координация с retention, **не атомарная транзакция между PostgreSQL и S3**. Незавершённое удаление (`deletionRequestedAt` установлен, `deletedAt` ещё нет) блокирует backup: сначала завершите/retry retention. Удалённые по политике объекты не требуются; их tombstone и история сохраняются.

## Настройки оператора

Загрузите эти переменные в текущий процесс из защищённой конфигурации/менеджера секретов. CLI не ищет `.env` и не выводит значения. Не передавайте URL с паролем в аргументах командной строки или в отчётах.

| Операция | Обязательные переменные |
|---|---|
| Backup | `BACKUP_DATABASE_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY` |
| Restore | `RESTORE_DATABASE_URL`, `RESTORE_S3_ACCESS_KEY_ID`, `RESTORE_S3_SECRET_ACCESS_KEY` |

Имя БД в явном `--source-database`/`--target-database` должно совпадать с URL. Для HTTP S3 разрешён только loopback; вне него требуется HTTPS. Регион по умолчанию `us-east-1`, другой задаётся `--region`. Параметры Prisma вроде `connection_limit` не передаются libpq; нестандартные параметры маршрутизации отклоняются.

## Создание и проверка

Родительский каталог должен существовать и быть доступен только оператору. Новый каталог backup **не должен существовать**. Файлам задаются режимы 0600/0700 там, где ОС их поддерживает; на Windows настройте приватный ACL родителя отдельно. Каталог не шифруется самим CLI: для переноса и хранения вне машины используйте зашифрованный носитель/хранилище и отдельное управление ключами.

```powershell
node scripts/backup-cli.cjs backup --output backups/recovery-2026-09-28 --source-database proctolearn_local --source-bucket proctolearn-local --source-s3-endpoint http://127.0.0.1:9000 --confirm-quiescent
node scripts/backup-cli.cjs verify --backup backups/recovery-2026-09-28
```

Успех — exit code 0 и `backup_verified`. Manifest/checksum публикуются после dump, копирования, проверки ссылок и повторного инвентаря. Ошибка оставляет неполный каталог для расследования; он не считается бэкапом и не перезаписывается повторным запуском. Следующий запуск получает новый каталог. `verify` проверяет целостность файлов, структуру и magic bytes custom dump; реальное выполнение восстановления подтверждает только roundtrip в новой БД.

Локальные имена файлов вычисляются из хеша S3 key: имя объекта не может превратиться в `../` путь на диске. Символические/жёсткие ссылки, лишние файлы, неверные пути, повреждённый manifest, отсутствующие объекты и несовпадающие хеши отклоняются. Лимит — 100000 объектов, manifest 32 MiB, одна операция передачи 5 минут, pg_dump/pg_restore 10 минут. Для более крупных данных нужен отдельно проверенный потоковый/инкрементальный процесс.

## Восстановление только в новый экземпляр

1. Оператор заранее создаёт **отдельную пустую БД** (например, из `template0`) и **отдельный пустой приватный bucket**. Имена/адреса отличаются от источника. Не используйте production БД как цель. Не запускайте API или cleanup на цели до проверки.
2. Проверьте bucket policy/IAM/ACL на цели: анонимное чтение и публичные grants должны быть запрещены. `--confirm-private-target` подтверждает эту проверку. Пустой bucket сам по себе не доказывает приватность. CLI дополнительно проверяет HTTP 403 для собственных нулевых пробных объектов в корне и каждом используемом префиксе, **до передачи приватных данных**. Пробы имеют случайные UUID и удаляются сразу; оператору нужны права создавать/читать объекты и удалять эти пробы. Это не универсальная проверка object-specific IAM/ACL разных провайдеров.
3. Задайте `RESTORE_*`, сначала выполните план, затем ту же команду с `--apply`:

```powershell
node scripts/backup-cli.cjs restore --backup backups/recovery-2026-09-28 --target-database proctolearn_recovery_20260928 --target-bucket proctolearn-recovery-20260928 --target-s3-endpoint http://127.0.0.1:9000 --confirm-quiescent --confirm-private-target
node scripts/backup-cli.cjs restore --backup backups/recovery-2026-09-28 --target-database proctolearn_recovery_20260928 --target-bucket proctolearn-recovery-20260928 --target-s3-endpoint http://127.0.0.1:9000 --confirm-quiescent --confirm-private-target --apply
```

План (`restore_plan_verified`) только читает цель и проверяет archive через `pg_restore --list`; пробные объекты в этом режиме не создаются. `--apply` после проверки приватности копирует объекты с условием `If-None-Match: *`, проверяет их байты, затем вызывает `pg_restore --single-transaction --exit-on-error --no-owner --no-privileges`. Ни `--clean`, ни `DROP`, ни автоматического создания БД/bucket нет. Любая непустая цель отклоняется. Нужен S3-провайдер с поддержкой conditional PUT; при отсутствии поддержки восстановление завершается ошибкой.

После этого проверяются таблицы/число строк, ссылки, **точный набор ключей и размеров** и SHA256 всех целевых объектов. Только тогда появляется `restore_verified`. При ошибке цель остаётся выключенной; уже скопированные объекты не удаляются автоматически. Для повтора создайте другую пустую пару БД/bucket. Инструмент не пытается «починить» или очистить ранее занятый экземпляр.

Проверьте вход тестового пользователя, сертификат, историю решения и воспроизведение камеры/экрана, а также отказ анонимному GET реальной записи. Настройте приложение на восстановленную пару БД/bucket, используйте отдельно сохранённые/перевыпущенные секреты и проверьте миграции до переключения трафика. Исходная БД/bucket остаются нетронутыми и служат вариантом возврата. Это не автоматический production cutover.

## Что не переносится автоматически

- SHA256 обнаруживает повреждение, но не доказывает доверенное происхождение. PostgreSQL dump может исполнять SQL: восстанавливайте только собственные доверенные копии. [Предупреждение PostgreSQL](https://www.postgresql.org/docs/current/app-pgrestore.html).
- Сохраняются текущие key/bytes/ContentType. Версии S3, delete markers, tags, ACL, bucket policy, lifecycle rules, KMS/IAM, некоторые дополнительные HTTP metadata и серверные роли PostgreSQL не архивируются. Настройте инфраструктуру отдельно. [Состав pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).
- Старые `EvidenceFile.url` с абсолютными URL не преобразуются автоматически в object keys. Если такой URL не совпадает с реальным ключом, backup откажет из-за отсутствующей ссылки. Для legacy MinIO сначала нужна отдельная проверенная миграция метаданных и объектов; нельзя исправлять только manifest, оставив неверную ссылку внутри dump.
- Старые локальные файлы, внешние видео уроков и сторонние системы не входят в этот backup. Нет обещания восстановить объект, который был удалён до копирования; tombstone сохраняется честно.
- Автоматический срок удаления backup не задан. Правила хранения и внешняя зашифрованная копия зависят от назначения проекта и требований владельца.

## Проверки в репозитории

Фактическая репетиция release 2026-10-10: `final-demo-20261010` получил `backup_verified`, отдельная новая пара — `restore_verified`; совпали инвентарь 25 таблиц, 32 объекта S3 (1 056 338 байт), ссылки и SHA256 объектов. Затем приложение действительно запускалось на восстановленной паре: браузерный вход, учебные материалы/пять завершённых уроков, одобренный результат, PDF/публичный QR, просмотр проктором и воспроизведение обоих синтетических потоков прошли; анонимный GET записей вернул 403. Отчёт хранится приватно в `.local/release-demo/evidence/restored-smoke.json`. После остановки восстановленной пары исходный профиль снова запущен; readiness, сохранность seed и оригинальные сценарии 4/5 и 5/5 повторно прошли. Это проверка локального восстановления, без утверждения о внешнем disaster recovery или физической камере.

```powershell
node --test scripts/backup-cli.test.cjs
# Из backend, с локальными TEST_DATABASE_URL, TEST_MINIO_* и при необходимости TEST_PG_BIN:
node --test test/integration/backup-restore.test.cjs
```

Интеграционный набор создаёт только собственные UUID БД/bucket на dedicated fixture, проверяет roundtrip настоящих байтов, audit/notifications, конкурентную advisory lock, отказ при занятых целях, повреждении/утрате файлов и незавершённом удалении. Затем удаляет только свои тестовые ресурсы.
