# Этап 2: секреты и гигиена репозитория

Дата: 26.09.2026. Исходная версия этапа: `4691a6c`. Изменения находятся в `fix/exam-security`, PR #2. Публикация коммита в этой ветке не означает слияние в `main` или обновление сервера.

## Подтверждённые находки

- В доступной истории Git Gitleaks 8.30.1 обнаружил Telegram bot token в старой версии `monitoring-project/docker-compose.yml` и шесть вхождений JWT в двух SQL-бэкапах. Это не проверка действительности токенов: они не использовались для входа или запросов к сервисам.
- Два остальных из девяти срабатываний стандартных правил — намеренно неверные токены в демонстрационных скриптах. Они заменены явной переменной с невалидным значением, без отключения стандартных правил сканера.
- В старых env-бэкапах есть значения переменных PostgreSQL, MinIO, JWT, n8n, Jenkins, pgAdmin и OPAL. Пароли небольшой сложности сканер может пропустить, поэтому они проверялись отдельно по именам переменных. Здесь значения не публикуются.
- Сырые `evidence/` содержали развёрнутую конфигурацию и служебные сведения. Два сборщика и общий setup-скрипт могли снова сохранить развёрнутую Compose-конфигурацию с секретами.
- Шаблоны окружения, Compose, Jenkins, MinIO и генераторы демо-пользователей использовали общедоступные пароли или запасные значения.

## Что изменено

1. Из текущего дерева Git исключены **114** локальных сгенерированных артефактов: сырые отчёты evidence, SQL демо-пользователей и TypeScript build info. Их локальные копии сохранены; история не переписывалась. Markdown-инструкции для защиты проекта сохранены.
2. `.gitignore` и проверка имён файлов блокируют приватные env, сырые evidence, дампы, ключи и сгенерированные аккаунты. Миграции и `.env.example` разрешены.
3. Пароли в примерах оставлены пустыми. Compose требует явные значения для паролей сервисов, n8n encryption key и OPAL-токенов. Необязательные Groq/Telegram/webhook-настройки не заменяются фиктивными рабочими ключами.
4. MinIO больше не получает запасной публичный пароль; Jenkins требует приватный пароль администратора длиной не менее 16 символов.
5. `seed.ts`, `seed-stepik.ts` и генератор `seed-users.sql` требуют явного `ALLOW_DEMO_SEED=true`, запрещены при `NODE_ENV=production` и используют переданные приватные демо-пароли. Пароли не печатаются. Старые пользователи не изменяются и не получают новые пароли от повторного seed.
6. Сборщики сохраняют список Compose-сервисов вместо развёрнутой конфигурации. Это уменьшает утечки, но не делает остальные диагностические отчёты автоматически публичными.
7. Добавлены Gitleaks с обычными правилами и двумя правилами для простых паролей в runtime-конфигурации, локальная проверка, необязательный pre-commit hook и отдельная CI-задача. Проверка индексированных файлов обнаруживает секрет даже тогда, когда рабочая копия уже очищена.

## Настройка окружения

Скопируйте нужный `.env.example` в приватный `.env`. Заполните секреты самостоятельно и не коммитьте файл. Для случайного значения используйте генератор криптографических случайных данных, например:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Для каждого пароля/ключа нужно отдельное значение. JWT access и refresh должны различаться. Для нативного backend задайте `DATABASE_URL`; Compose формирует внутренний URL из переменных PostgreSQL. При специальных символах в пароле URL требует процентного кодирования; случайный hex не требует его.

Не подставляйте случайную строку вместо `OPAL_CLIENT_TOKEN`: получите корректный клиентский токен в выбранной конфигурации OPAL. Изменение n8n encryption key без предусмотренной миграции может сделать существующие credentials нечитаемыми. Для существующих сервисов смена значения в `.env` сама по себе не гарантирует смену сохранённого пароля.

Для отдельной одноразовой демо-базы:

- `seed.ts`: `ALLOW_DEMO_SEED=true` и `DEMO_ADMIN_PASSWORD`, `DEMO_TEACHER_PASSWORD`, `DEMO_STUDENT_PASSWORD`, `DEMO_PROCTOR_PASSWORD` (каждый не короче 16 символов).
- `seed-stepik.ts`: opt-in и `DEMO_TEACHER_PASSWORD`.
- `generate-seed-sql.mjs`: opt-in и `DEMO_SEED_PASSWORD`. Сгенерированный SQL остаётся приватным локальным файлом. Не загружайте его в production.

Старые общие пароли из учебных инструкций больше не являются инструкцией для нового запуска. Для ранее созданных пользователей требуется отдельная ротация или удаление ненужных демо-аккаунтов.

## Проверка перед коммитом

Установите [Gitleaks 8.30.1 из официального релиза](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1), сверив SHA-256 с release checksums. Либо укажите путь к установленному бинарнику через `GITLEAKS_BIN`. CLI запускается локально, файлы не отправляются внешнему сканирующему сервису.

```bash
node --test scripts/check-secrets.test.cjs
node scripts/check-secrets.cjs
git add <проверенные-файлы>
node scripts/check-secrets.cjs --staged
```

Необязательная локальная установка hook:

```bash
git config core.hooksPath .githooks
```

В этой работе настройка hooks у владельца репозитория не менялась. CI использует закреплённую версию Gitleaks и SHA-256 Linux-архива; обнаружения редактируются, выводятся только имя правила, файл и строка. CI проверяет текущее дерево, а не объявляет старую историю чистой. Для отдельного исторического аудита: `gitleaks git . --redact=100`. Архивы, старые refs, форки и внешние копии требуют отдельного рассмотрения.

- Синтаксис изменённых Shell/PowerShell-скриптов проверен. Рабочее дерево и индекс просканированы с редактированием секретов.

## Что владелец должен сделать с ранее опубликованными доступами

Удаление файлов из нового коммита **не отзывает** секреты и не удаляет их из старых коммитов, `main`, форков или клонов. Пока PR не слит, старые файлы остаются и в текущем дереве `main`.

| Область | Действие в используемом окружении |
|---|---|
| Telegram | Отозвать опубликованный bot token и настроить новый у получателей уведомлений |
| JWT и пользовательские сессии | Заменить ключи подписи; отозвать старые сессии и проверить отказ старых токенов |
| PostgreSQL и MinIO | Сменить использованные пароли/ключи, обновить клиентов, проверить старые доступы |
| Jenkins / pgAdmin / Grafana / демо-пользователи | Сменить действующие общие пароли; отключить ненужные учётные записи |
| n8n | Сменить использованные пароли/webhook-секреты; отдельно спланировать миграцию encryption key с резервным восстановлением credentials |
| OPAL | Отозвать использованные master/client tokens и выпустить новые штатным способом |
| SMTP / AI-провайдеры и другие доступы | Проверить, использовались ли значения из старых файлов, и отозвать затронутые доступы |

Ротация на внешних сервисах в этом этапе не выполнялась. Ключи в чат присылать не нужно.

Очистка истории — отдельная операция после ротации: согласовать время, защитить приватную резервную копию, учесть все ветки/теги, удалить пути `backups/`, сырые `evidence/`, генерированные credential-выгрузки и вхождения ключей вне этих путей в отдельном клоне, повторить аудит и только затем согласовать force-push и обновление клонов. Такой force-push здесь не выполнялся. Для удаления кешированных ссылок и объектов следуйте [инструкции GitHub по чувствительным данным](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).
