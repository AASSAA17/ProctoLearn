# Вход и восстановление доступа

## Cookies и запросы

API выдаёт access и refresh JWT только через cookies. Ответы входа/регистрации содержат публичные поля пользователя; обновление сессии возвращает `{ok:true}`. В production cookies называются `__Host-pl-access` и `__Host-pl-refresh`, имеют `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` и не задают `Domain`. В development используются имена `pl-access` и `pl-refresh`. Срок cookies соответствует сроку JWT. JWT не сохраняются в localStorage и не передаются через параметры WebSocket.

Frontend и API должны быть на одном site: например, `https://app.example.com` и `https://api.example.com`. Размещение на независимых доменах несовместимо с выбранным SameSite=Lax. `FRONTEND_URL` — точный список разрешённых origins через запятую; в production обязателен HTTPS. Пути, query, credentials, wildcard и неуказанный localhost не принимаются.

Для любого изменяющего HTTP-запроса нужны разрешённый заголовок `Origin`, cookie и `X-CSRF-Token`. Перед запросом клиент получает `{csrfToken}` через `GET /auth/csrf` с credentials. Token хранится только в памяти и подписан с привязкой к отдельной HttpOnly cookie браузера. Вход/регистрация меняют эту привязку; выход и изменение/сброс пароля очищают её. Это относится также к анонимному входу, регистрации, восстановлению пароля и multipart-загрузкам. При `CSRF_INVALID` клиент один раз обновляет token и повторяет запрос. `ORIGIN_INVALID` не обходится повтором.

Для WebSocket проверяется точный Origin, access cookie и актуальные роль/версия сессии в базе. Проверка применяется к прямому WebSocket transport, а не только к CORS для HTTP polling. Ограничения назначений прокторов остаются обязательными.

## Обновление и отзыв

Refresh token одноразовый; база хранит его digest. Смена пароля, выход и административный сброс отзывают прежнюю версию сессии. Проверка версии выполняется на сервере, в том числе для уже подключённых сокетов. Неуспешный refresh не удаляет cookies ответом: запоздавший отказ не должен стереть сессию, уже обновлённую другой вкладкой.

Клиент координирует запросы одной вкладки и использует Web Locks между вкладками одного origin. Под блокировкой он сначала проверяет `/auth/me`, чтобы увидеть результат обновления другой вкладкой. Событие смены аккаунта сообщает вкладкам о необходимости заново загрузить пользователя, не передавая JWT. Web Locks требуют современного браузера и HTTPS/localhost.

Запросы известного пользователя сохраняют `X-Session-User` с его идентификатором. Сервер сверяет его с проверенной cookie до выполнения операции. Если в другой вкладке уже сменился аккаунт, ответ `409 AUTH_CHANGED` запрещает повтор исходной операции под новым пользователем, даже когда уведомление между вкладками запоздало. Выход координируется с refresh; сервер может очистить истёкшие cookies, но отзывает учётную запись только по проверенной подписи и версии сессии. При ошибке сети выход не объявляется успешным.

Существующая модель хранит одну цепочку refresh на пользователя: новый вход на другом устройстве заменяет её. Старый access действует до истечения срока или отзыва версии. Управление несколькими независимыми устройствами не добавлено.

## Восстановление пароля

Страницы `/auth/forgot-password` и `/auth/reset-password` используют одноразовую ссылку с ограниченным сроком. Backend хранит digest reset token. Повторное использование или просроченная ссылка отклоняются; успешный сброс отзывает сессии. Требования к новому паролю одинаковы при регистрации, смене и сбросе.

Письмо строит ссылку от первого разрешённого frontend origin и экранирует пользовательское имя. Для реальной доставки нужны настройки SMTP. Публичный ответ на запрос восстановления не сообщает, существует ли указанный email.

## Совместимость

После обновления старые клиенты с `Authorization: Bearer` должны перейти на cookie/CSRF API. Браузер удаляет старые JWT из localStorage; может потребоваться новый вход. Cookies уменьшают возможность кражи JWT через JavaScript, но не заменяют защиту от XSS: выполняющийся на разрешённом origin вредоносный код всё ещё может делать запросы от имени пользователя.

## Проверки этапа 6

Cookie/CSRF HTTP-тесты запускают настоящие Nest/Passport handlers и WebSocket transport. Проверяются cookie flags, Origin, подпись/срок CSRF, multipart до сохранения файла, отзыв сессии, ротация, несовпадение пользователя и отсутствие JWT в JSON. Frontend-тесты проверяют координатор, Axios retries и состояние пользователя при сбоях. Дополнительно Chrome с двумя настоящими вкладками и PostgreSQL подтвердил один refresh при одновременном истечении access, HttpOnly cookies, отсутствие logout на 503, сброс пароля и выход из другой вкладки. Доставка внешнего SMTP в эти проверки не входит.
