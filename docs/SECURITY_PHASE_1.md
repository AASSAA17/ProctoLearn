# ProctoLearn: исправления экзаменов, сессий и загрузки видео

База изменений: `be6495aca04b3e6e6ce3565eb3828f89ce769368` (`main`).
Рабочая ветка: `fix/exam-security`. Изменения не развёрнуты на сервере.

## Как получить изменения

Изменения подготовлены в отдельной ветке. Сначала сохраните свои незакоммиченные изменения.

```bash
git fetch origin
git switch --track origin/fix/exam-security
```

Если локальная ветка уже существует, сначала сопоставьте версии; не используйте принудительную перезапись. Старый patch первого этапа не содержит всех дополнений этого пакета. Перед запуском production подготовьте JWT, внешние адреса и миграции по инструкции ниже.

## Что изменено

- Повторяющиеся и чужие `questionId` отклоняются и DTO, и сервисом. Балл нельзя увеличить повторением правильного ответа.
- Начать экзамен может студент, записанный на курс. Пустые экзамены не запускаются. Лимит — пять попыток.
- Сервер проверяет срок сдачи. Предусмотрены фиксированные 5 секунд на доставку автоматической отправки; это не дополнительное время из клиентского запроса. Просроченная попытка закрывается как `FAILED`, поздние ответы не оцениваются.
- Начало попытки, отправка ответов и изменение Trust Score используют Serializable-транзакции с ограниченными повторами конфликтов. Ответы, результат, сертификат и завершение курса сохраняются атомарно.
- WebSocket проверяет текущую роль, JWT и владельца попытки. События ограничены DTO и размером сообщения. Истёкшие соединения закрываются; завершённые попытки не принимают новые штрафы. Неиспользуемый обработчик скриншотов удалён.
- Загрузка видео проверяет владельца до обработки файла и повторно в сервисе. Старый публичный `/uploads` отключён; записи должны выдаваться через защищённый evidence API и временные ссылки MinIO.
- Frontend дожидается последнего чанка рекордера и результата загрузки, сообщает о сбое. Параллельные HTTP-запросы используют одно обновление refresh token. Исправлена необъявленная переменная `hasCertificate`.
- JWT-ключи обязательны, не короче 32 символов и должны отличаться. Публичных fallback-ключей больше нет.
- Production Docker использует `/health`, `npm ci` и `prisma migrate deploy`, без автоматического seed и `--accept-data-loss`.
- Добавлены baseline исходной схемы, отдельная миграция `users.tokenVersion`, тесты и GitHub Actions.
- Next.js и eslint-config-next обновлены до 15.5.26. Обновлены совместимые версии axios, DOMPurify и части WebSocket-зависимостей в lock-файле.
- Refresh token хранится как SHA-256 полного токена, получает случайный `jti` и заменяется атомарно: повторное и конкурентное использование отклоняется. Старые bcrypt refresh-хеши не поддерживаются — нужен повторный вход.
- Logout, смена пароля, восстановление и административный сброс увеличивают версию сессии. REST проверяет её на каждом запросе; WebSocket — на сообщениях и каждые 30 секунд для простаивающего соединения. Изменение роли также закрывает старое соединение при следующей проверке.
- Ссылки восстановления хранятся в виде хеша, потребляются транзакционно и отзываются при смене пароля. Ранее выданные ссылки нужно запросить заново. Временные пароли администратора используют криптографическую случайность.
- Видео записывается во временный файл вне публичных каталогов, передаётся в MinIO через файловый поток и удаляется после обработки. Проверяются MIME и сигнатура контейнера; это не полноценный анализ видео. При ошибке сохранения evidence-записи загруженный объект удаляется по возможности.
- Для подписанных ссылок MinIO введён `MINIO_PUBLIC_URL`; внутренний Docker-host `minio` больше не требуется открывать в браузере. В production переменная обязательна. Nginx снимает `/api/`, допускает видео до 200 МБ плюс multipart-заголовки и увеличивает таймауты.
- Ошибка необязательных рекомендаций курсов не превращает уже сохранённый результат экзамена в HTTP-ошибку.
- `backups/` удалён из отслеживаемых файлов новой ветки. Локальные копии и старая история сохранены; опубликованные ранее секреты этим действием не отзываются.

Из `backend`:

```bash
npm ci --legacy-peer-deps
npm run prisma:generate
npm test
npm run build
```

Из `frontend`:

```bash

npm test
npm run typecheck
```

Это не заменяет сквозной прогон браузер → API → PostgreSQL → MinIO.

### Дополнительный этап: миграции и настоящая PostgreSQL

26.09.2026 на отдельной локальной PostgreSQL **18.3** повторно проверены:

- 41 backend-сценарий (модульные проверки и HTTP multipart) и production-сборка backend — успешно.
- Все 10 PostgreSQL-сценариев безопасности — успешно, включая конкурентные сдачи, refresh/logout и сброс пароля. Node выводит 11 тестов, поскольку считает также родительский тест.
- Два новых миграционных сценария — успешно: установка с нуля и обновление базы с исходной baseline. Повторный `migrate deploy` не меняет сохранённые данные; итоговая схема совпадает с `schema.prisma`.
- При обновлении сохранены исходные поля пользователей, пароли-хеши и связь студент → курс → преподаватель; существующим пользователям добавлен `tokenVersion = 0`.

Для повторения используйте **только отдельную тестовую БД**, задав `TEST_DATABASE_URL`, например `postgresql://test:TEST_PASSWORD@127.0.0.1:5432/proctolearn_security_test`:

```bash
npm run prisma:generate
npm run test:migrations
# Для сценариев безопасности сначала примените миграции к той же тестовой БД:
# DATABASE_URL должна указывать на эту тестовую БД, а не на рабочую.
npx --no-install prisma migrate deploy
npm run test:integration
```

`test:migrations` не использует обычную `DATABASE_URL` как запасной адрес. Он допускает только localhost/127.0.0.1 и имя БД `proctolearn_security_test`, создаёт случайную схему для каждого сценария и удаляет только созданную им схему в `finally`. После аварийного завершения процесса случайная схема может остаться в тестовой БД. Тестовому пользователю нужны права создания схем; таблицы `public` не очищаются. Тест обновления использует известную baseline и **не доказывает**, что схема действующей production-базы совпадает с ней.

Новый шаг включён в GitHub Actions перед PostgreSQL-сценариями безопасности. Локальный прогон на 18.3 не заменяет прогон CI на PostgreSQL 16. Frontend в этом дополнительном этапе не менялся и повторно не собирался.

Причина прежней остановки Actions подтверждена аннотацией [backend job](https://github.com/AASSAA17/ProctoLearn/actions/runs/36230756948/job/108373610622): `The job was not started because your account is locked due to a billing issue.` Владельцу аккаунта нужно устранить блокировку в настройках биллинга GitHub и повторить CI. До успешного прогона PR остаётся черновиком; изменение workflow само по себе не снимает блокировку аккаунта.

## Перед запуском: новые JWT-ключи

Сгенерируйте ключ дважды и сохраните два разных результата только в приватном `.env` / хранилище секретов:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Установите `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET`. Старые сессии после смены ключей перестанут работать — пользователям потребуется войти заново.
Проверьте `DATABASE_URL`, MinIO и `FRONTEND_URL` для выбранного окружения. Не копируйте значения из опубликованных резервных копий.

## ВАЖНО: существующая база данных

Не запускайте новую production-версию вслепую поверх старой БД.
Начальная миграция создаёт все таблицы для **пустой** базы. Для ранее созданной через `db push` базы её нужно корректно отметить как уже применённую.

1. Сделайте приватный бэкап и проверьте восстановление на отдельной копии.
2. Проверьте, что реальная схема соответствует **исходной baseline** `backend/prisma/migrations/20260926000000_baseline/migration.sql` (схема исходного коммита выше). Поле `users.tokenVersion` добавляет следующая отдельная миграция; не отмечайте её применённой вручную. При других расхождениях остановитесь: не отмечайте baseline применённой и не используйте `--accept-data-loss`.
3. Сначала на тестовой копии и только после проверки совпадения схемы выполните из `backend`:

```bash
npx --no-install prisma migrate resolve --applied 20260926000000_baseline
npx --no-install prisma migrate deploy
```

4. Повторите согласованный порядок для production. Если там уже есть история миграций, сначала согласуйте её с новой baseline — не заменяйте существующую историю.

Для новой пустой БД достаточно `prisma migrate deploy`. Демо-данные теперь загружаются только явно через `npm run seed` в выбранную демо-базу; не запускайте seed на рабочих данных.

Официальная справка: [Prisma baselining](https://www.prisma.io/docs/orm/prisma-migrate/workflows/baselining).

## Внешние адреса и запуск

Production использует `docker-compose.yml`: `NODE_ENV=production` задан явно. `docker-compose.server.yml` остаётся историческим демо-стеком с dev-образами и не является production-конфигурацией.

Установите `FRONTEND_URL` в точный HTTPS origin сайта, `NEXT_PUBLIC_API_URL=https://ваш-домен/api`, `NEXT_PUBLIC_WS_URL=wss://ваш-домен`. Публичные переменные Next.js задаются перед сборкой.

Для видео задайте `MINIO_PUBLIC_URL` как доступный браузеру origin, например `https://storage.example.com`, и соответствующий `MINIO_REGION`. Нужен отдельный домен с HTTPS, проксируемый к S3-порту 9000; пример — `nginx/minio.conf.example`. Консоль 9001 не требуется публиковать. Нельзя добавлять префикс пути к подписанному URL. Приватность bucket и воспроизведение Range-запросами нужно проверить в целевой среде.

При первом запуске после миграции пользователи входят заново. После смены пароля интерфейс также направляет на вход. Перед развёртыванием проверьте `nginx -t`, healthcheck, вход/выход, экзамен, запись камеры/экрана и воспроизведение доказательств на тестовом окружении.

## Что ещё не закрыто

- Возможные секреты в старой истории и других файлах, включая журналы. Требуются отдельный аудит, ротация реальных доступов и согласованная очистка истории. Реальные ключи не использовались и не менялись.
- Браузер пока держит запись в памяти; отсутствуют chunk-upload, возобновление и надёжная очередь. На сервере нужны квоты диска и уборка временных файлов после аварийного завершения процесса. При сбое загрузки результат экзамена сохранён, но доказательства могут отсутствовать.
- Токены браузера пока хранятся в localStorage. Вкладки используют общий refresh token, но синхронизация обновлений между отдельными вкладками не реализована; одновременное обновление в двух вкладках может потребовать повторного входа.
- Камера/демонстрация экрана не являются доказательством личности. Нет полноценного компьютерного зрения, серверного heartbeat, устойчивого сохранения ответов и проверки обязательности видеодоказательств перед сертификатом.
- `FLAGGED` по-прежнему блокирует сдачу. Для реального применения нужны ручной разбор, апелляция и явная политика ложных срабатываний.
- Политика срока хранения видео, удаления данных и ограничения доступа конкретных преподавателей/прокторов требует отдельного этапа.
- Остались предупреждения npm audit: frontend после обновления — 0 critical, 3 high, 2 moderate (включая транзитивные зависимости). Это не утверждение, что приложение полностью защищено; нужно отдельно проверить совместимое обновление остальных зависимостей. Backend-зависимости этим этапом полностью не аудировались.
- Настройки nginx, внешние адреса MinIO, браузерные разрешения, production Docker и реальная сеть требуют smoke-теста выбранного окружения перед публикацией.

Справка об исходной проблеме Next.js: [официальный security advisory](https://nextjs.org/blog/CVE-2025-66478).
