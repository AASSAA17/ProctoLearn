# Записи и апелляции

## Сохранение записи

Каждый запуск MediaRecorder получает отдельный UUID для камеры и экрана. Браузер сохраняет фрагменты в IndexedDB перед передачей на сервер. После перезагрузки прежние сегменты дозагружаются с отметкой прерывания; новый MediaRecorder создаёт новый сегмент. Записи разных запусков не склеиваются в один WebM.

Сервер принимает фрагменты на диск, считает SHA-256 и фиксирует номер, размер и хеш в PostgreSQL. Повтор с теми же байтами безопасен; другой фрагмент с тем же номером отклоняется. Завершение требует непрерывной последовательности индексов, сверяет хеши при потоковой сборке и создаёт EvidenceFile только после загрузки результата в хранилище. Блокировка с ограниченным сроком позволяет повторить сборку после сбоя процесса. При неизвестном исходе записи в БД объект сохраняется минимум 24 часа: транзакция может завершиться после потери ответа. Очистка повторно проверяет ссылки, прежде чем удалить аварийный объект.

Проверка заголовка контейнера и хешей подтверждает формат и целостность передачи. Она не удостоверяет личность, подлинность источника видео или непрерывное присутствие человека. Проктор должен просмотреть сегменты, прерывания и события перед решением.

Текущие ограничения:

- Один транспортный фрагмент: до 8 MiB; браузер делит большие события на фрагменты по 2 MiB.
- Все сегменты одной попытки: до 512 MiB, до 12 сессий и до 8192 фрагментов на сессию. Отмена не обнуляет квоту. Единственная открытая апелляция добавляет ещё 512 MiB для восстановления сохранившихся локальных записей; суммарный предел за всю историю попытки — 1 GiB. Повторное обращение не увеличивает его.
- До запуска таймера браузер проверяет оценку объёма записи и свободного места. Целевой битрейт рассчитан в том числе на экзамен длительностью 60 минут; фактический размер зависит от кодека и содержимого. Слишком длительный экзамен требует изменения политики хранения или длительности.
- Запись требует HTTPS либо localhost, MediaRecorder, IndexedDB и Web Locks. Блокировка между вкладками защищает работающую запись от ошибочного восстановления во второй вкладке.
- Дозагрузка разрешена владельцу в течение 24 часов после завершения/дедлайна. После решения проктора изменение закрывается. Открытая апелляция даёт одно новое окно в 24 часа; повторы запроса не продлевают его.
- Локальные фрагменты удаляются после подтверждения полного результата. При ошибке копия сохраняется для повторной отправки; удаление профиля браузера или его данных уничтожает эту копию.
- Если сервер уже отменил просроченный сегмент, восстановление выполняется явно в новую сессию. Локальное перенесение фрагментов атомарно, а прежняя серверная сессия остаётся в истории.

Старый POST `/evidence/:attemptId/recording` отвечает 410 и требует обновить страницу. Ранее сохранённые записи остаются доступны назначенным проверяющим.

## API

Все операции загрузки требуют аутентификации и принадлежности попытки текущему пользователю. Доступ проверяется до приёма multipart-файла и повторно внутри транзакции.

| Запрос | Назначение |
|---|---|
| GET `/attempts/preflight/:examId` | Длительность, оставшееся время и бюджет записи без создания попытки |
| POST `/evidence/:attemptId/uploads` | Идемпотентное создание по `kind`, `clientSessionId`, `mimeType` |
| GET `/evidence/:attemptId/uploads` | Список собственных сессий |
| GET `/evidence/uploads/:id` | Состояние и манифест без внутренних ключей хранилища |
| PUT `/evidence/uploads/:id/chunks/:index` | Multipart с одним полем `file` |
| POST `/evidence/uploads/:id/complete` | `expectedChunks`, необязательное `interrupted` |
| POST `/evidence/uploads/:id/abort` | Отмена незавершённой сессии; готовую запись удалить нельзя |

## Проверка и апелляция

Для выдачи сертификата нужны проходной результат по сохранённым правилам экзамена, обе записи и решение независимого от студента проверяющего. Незавершённые загрузки блокируют выдачу. Отменённые/прерванные сегменты видны проверяющему; наличие технически завершённого файла не означает автоматическое одобрение.

Владелец завершённой отклонённой попытки может подать одну апелляцию с причиной. Повтор той же причины возвращает существующий запрос. Рассматривает назначенный проктор или администратор, который не является студентом и не принимал исходное решение. Решение `UPHELD` оставляет отказ, `OVERTURNED` меняет его на одобрение только при выполнении требований к результату и записям.

Первое решение и решение по апелляции сохраняются в отдельной истории. Апелляция, новое решение, сертификат и завершение курса фиксируются одной транзакцией. Статус открытой апелляции отображается в очереди проктора.

API: GET/POST `/proctor/sessions/:attemptId/appeal` (`reason`); POST `/proctor/sessions/:attemptId/appeal/resolve` (`decision`, `reason`). Причина: 3–2000 символов. Изменять уже зафиксированное решение через повторный запрос нельзя.

## Очистка временного хранения

Операторская команда работает с окружением выбранного развёртывания. Она не создаёт bucket и не выводит секреты. После сборки backend:

```sh
npm run recordings:cleanup
npm run recordings:cleanup -- --apply
```

Первый запуск только показывает план. `--apply` удаляет временные фрагменты закрытых/просроченных сессий и старые объекты, отсутствие ссылок на которые подтверждено в БД. Готовые доказательства сохраняются. Для аварийных объектов и локальных временных файлов применяется запас в 24 часа. Активная сборка и новое окно апелляции защищены от очистки.

Команда обрабатывает ограниченную партию и возвращает `continuation`. Продолжайте сканирование с непустыми `--uploads-cursor=...`, `--staging-cursor=...`, `--finals-cursor=...`, пока соответствующие значения не станут null. В контейнере команду можно вызвать через `docker compose exec -T api npm run recordings:cleanup`. Это очистка временных файлов; срок хранения готовых доказательств задаётся отдельно.

## Проверки

Сценарии PostgreSQL проверяют гонки загрузки/квоты/завершения, повтор после потери подтверждения, откат решений и выдачи сертификата. `npm run test:storage` требует отдельную локальную PostgreSQL и S3 на порту 19000; без настройки тест завершается ошибкой, а не пропускается. CI поднимает отдельный контейнер и проверяет прочитанные из хранилища байты, повреждение фрагмента и откат после ошибки БД.

MinIO Community архивирован. Образ в CI зафиксирован по digest и используется как изолированная проверка совместимости S3, а не как рекомендация для production: [официальный репозиторий](https://github.com/minio/minio), [образ с указанной версией](https://hub.docker.com/r/minio/minio/tags). Выбор поддерживаемого хранилища относится к инфраструктурному этапу.
