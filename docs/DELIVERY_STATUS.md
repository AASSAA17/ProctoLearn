## Принятые правила доступа

- Общедоступен каталог и оглавление. Материалы доступны записанному студенту, автору курса и администратору.
- Ключи заданий доступны только автору/администратору. История ответов студента не раскрывает ключ следующей попытки.
- Преподаватель управляет своим курсом и видит его результаты; администратор управляет всеми курсами.
- Проктор видит попытки, события и записи только назначенных экзаменов. Назначение/отзыв делает автор курса или администратор.
- API назначений: GET `/proctor/exams/:examId/assignments`, PUT/DELETE `/proctor/exams/:examId/assignments/:proctorId`.
- Отзыв проверяется перед доставкой событий даже для уже открытого WebSocket. Уже выданная ссылка на запись действует не более пяти минут.

## Этап 4: сдача и проверка

Попытка сохраняет версию вопросов, ключей, длительности и проходного балла. Последующие правки экзамена не меняют её оценку. Черновик сохраняется на сервере с номером ревизии; конкурирующая вкладка получает конфликт вместо перезаписи ответов. После истечения времени сервер оценивает только сохранённый черновик. Открытие истории также завершает просроченную попытку; постоянный фоновый обработчик пока не добавлен.

Повтор той же сдачи возвращает сохранённый результат, другие ответы после завершения отклоняются. Камера и экран запрашиваются до запуска таймера. Ошибки сохранения/загрузки видны в интерфейсе. Флаги прокторинга и нулевой trust не блокируют отправку ответов.

Допуск учитывает обычные и модульные уроки, успешные TASK и проверенные письменные задания. Административный допуск сохраняется отдельно с идентификатором администратора и не создаёт вымышленные выполнения уроков. Административный сертификат имеет источник `ADMIN_OVERRIDE`.

Сертификат по экзамену выдаётся только после проходного результата, наличия записей камеры и экрана и решения назначенного проктора/администратора. Самопроверка запрещена. Решение, причина, проверяющий, сертификат и завершение курса сохраняются одной транзакцией; одинаковый повтор безопасен, противоречивый отклоняется. Студент видит статус и причину проверки.

Миграция сохраняет исторические сертификаты с источником `LEGACY`. Старые версии вопросов восстановить невозможно: прежние попытки получают снимок состояния на момент обновления. Старые отметки просмотра не принимаются за проверенное письменное задание. Устойчивое хранение записей частями, контроль полноты и апелляции описаны ниже.

## Этап 5: записи и апелляции

Фрагменты камеры и экрана сначала сохраняются в IndexedDB, затем отправляются с повторами после потери сети или подтверждения. Перезагрузка восстанавливает незавершённые сегменты; Web Lock защищает работающий экзамен от второй вкладки. До старта таймера проверяется бюджет хранения. Сервер ограничивает объём, проверяет хеши, собирает поток на диск и связывает готовый файл с попыткой транзакционно. При неизвестном исходе транзакции объект удерживается минимум 24 часа, после чего очистка снова проверяет ссылки. Команда очистки по умолчанию только показывает план.

Решения проверяющих сохраняются в истории. Студент может подать одну апелляцию; её рассматривает другой назначенный проверяющий. Одобрение требует обеих завершённых записей и проходного результата. Восстановление записи во время апелляции имеет отдельное ограниченное окно и дополнительную квоту. API, ограничения и команды: [RECORDINGS_AND_APPEALS.md](RECORDINGS_AND_APPEALS.md).

## Этап 6: сессии и восстановление доступа

JWT перенесены в HttpOnly cookies, в production — Secure/SameSite=Lax/__Host-. API не возвращает JWT в JSON; фронтенд удаляет прежние localStorage tokens. Все изменяющие HTTP-запросы требуют точный разрешённый Origin и подписанный CSRF token. WebSocket проверяет Origin и cookie с актуальной ролью/версией сессии. Повтор запроса после смены аккаунта блокируется сверкой исходного пользователя на сервере.

Вкладки координируют refresh и выход через Web Locks; ошибки сети/сервера сохраняют состояние и дают повторить проверку. Добавлены страницы восстановления пароля, общая политика пароля при регистрации/смене/сбросе, безопасные ссылки и HTML писем. Настройки и ограничения: [AUTH_SESSIONS.md](AUTH_SESSIONS.md).

Проверки 28.09.2026: backend build и 146 тестов; 10 сценариев с настоящей PostgreSQL (11 тестов с родительской группой), включая гонки refresh/logout/reset. Frontend: 52 теста и production build. Chrome с настоящими cookies, двумя вкладками и PostgreSQL подтвердил ротацию один раз, сохранение состояния при 503, reset и logout. Production cookies проверены через HTTP headers; реальный SMTP и production HTTPS требуют целевого окружения.
