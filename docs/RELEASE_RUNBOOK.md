# Проверка и выпуск ProctoLearn

## Что является проверенным стендом

GitHub Actions `Platform checks` создаёт одноразовый `proctolearn-local` из `docker-compose.local.yml` с новыми volumes, применяет миграции при старте API, добавляет demo seed, проверяет readiness PostgreSQL/S3, четыре роли, экзамен, браузерную запись и воспроизведение. Затем `scripts/release-smoke.cjs` выполняет 60 параллелизованных **только читающих** запросов каталога (не более шести одновременно), требует ноль ошибок и p95 не более 3000 мс на runner CI. Это воспроизводимая smoke-нагрузка, не расчёт предельной пропускной способности production.

Отдельный backend job проверяет чистое применение миграций, повторное применение и совместимость с историей на PostgreSQL; настоящий S3 fixture проверяет backup/restore в **новую пустую** БД и bucket, точные байты объектов, ссылки и отказ при повреждении. См. [BACKUP_RESTORE.md](BACKUP_RESTORE.md), [BROWSER_E2E.md](BROWSER_E2E.md). Release gate: все четыре job (`secrets`, `backend`, `frontend`, `local-stack`) зелёные на том же commit SHA, который планируется развернуть. Нельзя считать зелёным старый SHA или только часть jobs.

Локальная проверка smoke разрешена только на loopback стенде:

```powershell
node scripts/release-smoke.cjs http://127.0.0.1:4000/
```

Скрипт отвергает внешние адреса и не посылает изменяющих запросов. Он не запускает старый `scripts/load-test.sh`: тот демонстрирует Telegram/AlertManager, использует широкую нагрузку и не является релизным критерием.

## Подготовка целевого окружения

1. Зафиксировать commit SHA и URL зелёного workflow, целевой домен/сервер, время обслуживания, администратора выпуска и способ вернуть трафик. Оценить объём БД и bucket, свободное место, версию PostgreSQL, переменные и срок хранения записи. Получить разрешение владельца на реальную выкладку и правила обработки данных/внешнего AI.
2. Подготовить отдельные staging БД/bucket и приватные секреты. Проверить HTTPS, `FRONTEND_URL`, публичный S3 endpoint, cookie/CSRF, SMTP, доступность `GET /ready`, анонимный отказ в чтении объектов. `GROQ_API_KEY` необязателен; см. [AI_CAPABILITIES.md](AI_CAPABILITIES.md).
3. Проверить политику миграций и выделить окно без записей. Снять согласованную копию PostgreSQL + S3 по [BACKUP_RESTORE.md](BACKUP_RESTORE.md), выполнить `verify`, затем восстановить её в другую пустую пару и вручную проверить вход, сертификат и записи. Сохранить исходную пару для возврата. Старые абсолютные MinIO URL требуют отдельной миграции; инструмент остановится, если обнаружит несоответствие.
4. На **staging** применить release SHA с `prisma migrate deploy` и проверить `GET /ready`, авторизацию всех ролей, создание/сдачу экзамена, обе записи, просмотр проктором, аудит и письма. Физическую камеру/выбор экрана, Safari/Firefox и экранный диктор проверить вручную: автоматический сценарий их не покрывает. Затем запустить bounded smoke на loopback staging API и зафиксировать результат.
5. Перед переключением production трафика убедиться, что staging и целевая конфигурация совпадают по версиям приложения/схемы и storage semantics. Сравнить `git rev-parse HEAD` с SHA зелёного CI. После переключения проверить `/ready`, сайт, вход и реальные ключевые сценарии, мониторинг ошибок, задержки и заполнение storage. Не публиковать секреты в отчёте.

## Возврат при неудаче

Если ошибка обнаружена до переключения, оставить production нетронутым. Если после переключения и данные **не менялись**, вернуть прежний код и трафик на прежнюю согласованную пару БД/bucket. Если новая версия успела записать данные, не запускать старый код поверх новой схемы вслепую: остановить записи, сохранить текущий экземпляр для расследования и восстановить исходную проверенную копию в **другую пустую** пару. Переключить трафик только после проверки целостности и согласования допустимой потери изменений за окно выпуска. Автоматического `migrate down` и перезаписи рабочей БД нет.

## Текущая граница проверки

`docker-compose.yml` и `docker-compose.server.yml` помечены `legacy` и не подтверждены как целевая production-конфигурация. Одноразовый локальный стенд CI не заменяет сервер владельца. В репозитории нет адреса production, доступа, домена/TLS, внешней БД/S3, политики хранения и согласованного окна обслуживания; поэтому реальный production deploy и его откат нельзя считать выполненными. До получения этих данных результат этапа — проверенный release candidate и инструкция оператору, а не объявление о работающем production.
