# Хранение экзаменационных записей

Этап 8, 28 сентября 2026 года. Эта политика относится к видео доказательств в S3 и их состоянию в БД. Она не удаляет аккаунты, ответы, оценки, решения прокторов, апелляции, сертификаты или журнал аудита. Юридический срок хранения организация определяет отдельно; код не объявляет какой-либо срок обязательным по закону.

## Включение и предварительный просмотр

По умолчанию удаление выключено: `EVIDENCE_RETENTION_DAYS` отсутствует или пуст. Чтобы включить политику, оператор явно задаёт целое число от 1 до 36500. Ноль, отрицательное, дробное, пробелы и другие ошибочные значения отклоняются. Приложение не запускает удаление автоматически при старте и не устанавливает расписание.

Из каталога `backend`, после сборки и с явно заданным окружением развёртывания:

```sh
# Сначала посмотреть временные части, затем при необходимости очистить их.
npm run recordings:cleanup
npm run recordings:cleanup -- --apply

# Политика финальных записей: только предварительный просмотр.
npm run evidence:retention

# Реальное применение — отдельное явное действие оператора.
npm run evidence:retention -- --apply
```

Обе команды работают ограниченными страницами. Для финальных записей размер страницы по умолчанию 100, допустимо `--limit=1` … `--limit=1000`. Продолжение: `--cursor=<nextCursor>` из предыдущего ответа. Можно сузить запуск до одной попытки: `--attempt-id=<UUID>`. Даже защищённые записи включены в просмотр и не мешают продолжить сканирование при использовании курсора. Следующий полный проход начинается без курсора, чтобы повторить неудавшиеся задания.

Без `--apply` команда не меняет БД, журнал или S3. Вывод содержит только ID и безопасные коды результата; в нём нет ключей объектов, URL, имён студентов, токенов или диагностик провайдера. Код завершения 0 означает законченный проход, 1 — ошибку конфигурации/выполнения, 2 — наличие `RETRY` или `PROTECTED_OR_BUSY`. Наличие защищённых файлов само по себе не является ошибкой.

## Какие записи можно удалить

Срок отсчитывается от самой поздней даты: создания файла, окончания попытки, последнего решения проктора или решения апелляции. Старый файл с новым решением не удаляется досрочно.

Файл допускается к удалению только у завершённой попытки (`FINISHED`/`FAILED`) с окончательной проверкой. Блокируются:

- активная попытка или `PENDING`/незаполненная дата проверки;
- административный запрет хранения `evidenceLegalHold`;
- открытая или незавершённая апелляция;
- `REJECTED` без уже закрытой апелляции: действующая модель не ограничивает срок подачи единственной апелляции, поэтому такие записи сохраняются бессрочно;
- любой `OPEN`/`FINALIZING` upload или действующая аренда сборки;
- оставшиеся строки временных частей (`STAGED_CHUNKS_REMAIN`), даже для `COMPLETE` upload: сначала требуется существующая очистка временных частей;
- чужой/неподдерживаемый ключ объекта, абсолютный URL или подозрительный путь. Автоматически поддерживается только пространство `recordings/<attemptId>/…`; старые форматы требуют отдельной проверенной миграции.

Физические временные части, не связанные с БД из-за неизвестного результата транзакции, очищаются существующей процедурой `recordings:cleanup` после её защитного срока. Удаление финального файла не означает стирание всех резервных копий или неизвестных старых объектов. Жизненный цикл бэкапов настраивается отдельно; не следует включать неограниченное S3 lifecycle-удаление поверх защищённых записей.

## Запрет удаления

Администратор может вызвать защищённый cookie/CSRF endpoint:

```http
POST /evidence/:attemptId/hold
Content-Type: application/json

{"onHold":true,"reason":"Проводится дополнительное расследование"}
```

`reason` обязателен, 3–2000 символов; `onHold:false` снимает запрет. Ответ: `{attemptId,onHold,reason,changedAt}`. Причина хранится в защищённой записи попытки; общий аудит содержит только `attemptId` и `onHold`. Проктор видит наличие запрета, причина доступна администратору в сводке.

До первой отправки удаления запрет отменяет ожидающие задания и возвращает файлы в `AVAILABLE`. После первой попытки отправки S3-удаления запрет возвращает `409 RETENTION_ALREADY_STARTED`. Даже сетевой сбой не доказывает, что S3 не успел удалить объект, поэтому API не обещает сохранность в этой ситуации. Этот отказ действует и после истечения аренды задания. Снятие или установка запрета не восстанавливает уже удалённые байты.

## Устойчивость к сбоям и параллельным операциям

Перед отправкой удаления транзакция сохраняет `EvidenceFile.deletionRequestedAt` и `EvidenceDeletionJob`. При запуске работника фиксируются номер попытки, токен и аренда на 5 минут. Все допуски повторно проверяются; блокировка строки попытки упорядочивает запрет удаления и начало обработки.

Удаляется только точный ключ выбранного файла. После подтверждённого ответа S3 другая часть транзакции устанавливает `deletedAt`, состояние задания `DONE` и запись аудита. Метаданные файла, решения и сертификаты остаются. Сбой S3/БД оставляет tombstone и безопасный код `STORAGE_OR_DATABASE_FAILURE` в задании `RETRY`; неизвестные исходы также считаются незавершёнными. Аренда сохраняется до исходного истечения даже при ошибке: результат транзакции может прийти поздно. Повтор возможен через следующий проход после истечения этих 5 минут; до этого результат — `PROTECTED_OR_BUSY`. Если процесс оборвался, после истечения аренды следующий проход повторяет идемпотентный `DeleteObject`. Завершение сравнивает токен аренды, поэтому устаревший работник не публикует чужое задание. Исчезнувший объект и потерянный ответ не приводят к потере задания.

S3-операция ограничена 30 секундами с реальным отменяемым запросом, транзакция удаления — 45 секундами. Новые задания и удаление используют PostgreSQL advisory lock `71083208`, общий с оператором резервного копирования. Бэкап должен удерживать эту блокировку и отклонять незавершённые tombstone (`deletionRequestedAt != null && deletedAt == null`). Это координация этих процедур, а не универсальный атомарный снимок S3; остальные процессы записи и очистки останавливаются по инструкции резервного копирования.

## Чтение и сертификаты

`GET /evidence/:attemptId` сохраняет существующие ограничения для назначенного проктора/администратора. Запись возвращает `id`, `attemptId`, `type`, `createdAt`, `deletionRequestedAt`, `deletedAt` и состояние:

| Состояние | Значение | URL |
| --- | --- | --- |
| `AVAILABLE` | Запись доступна | Подписанный на 5 минут |
| `DELETION_PENDING` | Удаление ожидает или повторяется; байты могут уже отсутствовать | Нет |
| `DELETED` | Удаление подтверждено и зафиксировано | Нет |

Сводка проктора содержит те же безопасные метаданные без S3-ключей и URL. Ранее выданный URL может оставаться пригодным до собственного истечения или удаления объекта; новая ссылка после tombstone не выдаётся. Состояние `RecordingUpload.COMPLETE` означает исторически завершённую загрузку, а не бессрочную доступность файла; для доступности используется состояние EvidenceFile.

Удаление не отзывает выданный сертификат. Новая экзаменационная выдача проверяет, что записи камеры и экрана не имеют ни `deletionRequestedAt`, ни `deletedAt`. Административный обход выдачи остаётся отдельным аудируемым действием с существующими правами.

## Проверки

Автоматические тесты используют только отдельную локальную БД `proctolearn_security_test`, случайные UUID и собственный тестовый S3 bucket. Проверяются отключённая политика и dry run, защищённые состояния, возраст после последнего решения, сокрытие ключей, отмена ожидающего задания запретом, конфликт запрета после отправки удаления, создание апелляции параллельно очистке, восстановление истёкшей аренды, два работника, блокировка резервного копирования, курсоры, оставшиеся временные части и сохранение сертификата.

Тест на настоящем SeaweedFS/S3 удаляет только выбранный тестовый ключ, моделирует потерю ответа после фактического удаления, затем проверяет успешный повтор и неизменность соседнего объекта. Эти тесты не удаляют существующие рабочие данные.
